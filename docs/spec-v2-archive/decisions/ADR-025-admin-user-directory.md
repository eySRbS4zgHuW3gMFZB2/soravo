# ADR-025 — Admin user directory query surface

Status: Accepted
Date: 2026-09-16

Context: CLOUD-013 delivers the final PRD §7 admin-dashboard query surface, the user directory: searchable per-user rows — a unique public user ID, email/account identity, subscription status, device/session information, account status, and relevant timestamps — served to the admin dashboard owner (01_PRD.md §7). ADR-016 established the SECURITY DEFINER pattern (in-body admin gate FIRST, `search_path = pg_catalog`, schema-qualified references, no dynamic SQL, EXECUTE to `authenticated` only) for cross-user reads; ADR-022 establishes that `public.profiles.role` is the singular server-authoritative admin flag. Two gaps block the directory under the ADR-016 shape: (1) the directory, unlike metrics, returns raw per-user data, so the leak surface is rows not counts — the projection must be minimized and safe by construction; and (2) PRD §7 requires a "user unique ID", but internal UUIDs (`auth.users.id`, `public.profiles.id`) are private identifiers that must never leave the server. Every authenticated session is RLS-scoped to its own rows (CLOUD-002), so a plain SECURITY INVOKER function or `security_invoker` view can never read other users' rows even for an admin — the directory, like metrics, must be privileged yet gated.

Decision: Expose exactly one new SECURITY DEFINER function in `public`, `admin_users(p_search text default null, p_offset integer default 0)` returning `jsonb`, callable only by the `authenticated` role through PostgREST RPC, performing its own server-side admin gate FIRST inside the body (`raise exception 'CLOUD-013: admin access required'` when `auth.uid()` is null or the caller's `public.profiles.role <> 'admin'`). This is the third justified SECURITY DEFINER exception (ADR-010 escape hatch, alongside ADR-016's metrics trio) and is added to the `db_assertions.sql` check 16 whitelist.

Two data-shape decisions:

- A server-owned, immutable public user ID: add `public.profiles.public_user_id text NOT NULL UNIQUE CHECK (CHAR_LENGTH(public_user_id) BETWEEN 8 AND 200)`. Value = `'user-' || replace(gen_random_uuid()::text, '-', '')` (lowercase hex, 37 chars, `gen_random_uuid()` ships in `pg_catalog` on Postgres 13+ so no extension/cost worry). It is generated ONLY by a `BEFORE INSERT` trigger `profiles_set_public_user_id` that overwrites any client-supplied value (server ownership), and made immutable by `BEFORE UPDATE` trigger `profiles_guard_public_user_id_immutable` which raises `CLOUD-013: public_user_id is immutable` for EVERY session, including `postgres`. Both triggers are `SECURITY INVOKER`, `set search_path = pg_catalog`, and have EXECUTE revoked from `public`/`anon`/`authenticated`/`service_role`. The column is populated by the migration backfill before `SET NOT NULL`, so existing and future rows are always keyed. This satisfies "user unique ID" without leaking internal UUIDs.
- A canonical, bounded, deterministic query: `ORDER BY lower(u.email) COLLATE "C", u.id` (byte-stable), page size fixed at 25 (`limit 26 + offset`, `has_more` via slicing the 26th element, page_size echoed as 25), offset `coalesce(p_offset, 0)` validated `< 0` → raise `CLOUD-013: p_offset must be non-negative` and `> 100000` → raise `CLOUD-013: p_offset may not exceed %`, 100000. Search is `position(lower(v_search) in lower(col)) > 0` — a literal case-insensitive substring over `u.email`, `u.public_user_id`, and `p.display_name`, immune to `LIKE` meta-character issues; the input is trimmed, `''` → NULL, and truncated to 100 chars (`left(..., 100)`) so arbitrary client strings stay bounded and never reach query text.

Return contract (closed, minimal):

- Envelope: `{ users, has_more, page_size, offset, search, generated_at }`. Timestamps serialized `to_char(at time zone 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS"Z"')`; `search` echoes the normalized input; `generated_at` is wall-clock (the only non-deterministic field, excluded by the determinism test).
- Per user — exactly 11 keys: `public_user_id, email, display_name, role, account_status, created_at, updated_at, last_sign_in_at, entitlement, devices, sessions`. `account_status` is derived `'deleted'` (`auth.users.deleted_at` set) / `'banned'` (`banned_until` set) / `'active'` otherwise. `entitlement` is the newest `product = 'soravo'` row projected to `{plan, status, starts_at, expires_at}` (JSON null when none). `devices` = `{count, active, platforms, last_seen_at}` and `sessions` = `{count, active, last_seen_at}` — counts plus minimal summaries, never session hashes, provider/payment references, auth identities, passwords, or `raw_user_meta_data`.
- The `LEFT JOIN LATERAL` on `public.devices`/`public.sessions` uses correlated scalars (`count(*) filter (where revoked_at is null)`, `jsonb_object_agg(platform, 1)`, `max(last_seen_at)`) so aggregates always yield an object even for zero-count users.

The privilege elevation is contained exactly as in ADR-016: gate runs FIRST; stored `profiles.role` is the only authority (tampered `role`/`user_metadata.role` claims grant nothing); EXECUTE revoked from `public`, `anon`, `service_role`, granted to `authenticated` only; `search_path = pg_catalog`; every object schema-qualified; no dynamic SQL. The directory adds NO table grants, policies, or new writes — `public_user_id` lives on the existing `public.profiles` table and is only ever machine-generated.

Alternatives:
- Expose `auth.users.id`/`profiles.id` directly (rejected: internal UUIDs are account identifiers that leak across the network and enable correlation; PRD §7 asks for a user-facing unique ID, so we mint a dedicated opaque key).
- Client-generated `public_user_id` (rejected: client-supplied identity is spoofable and undermines its purpose as a stable server address; ADR-022 precedent — server-authoritative identity).
- A `SECURITY INVOKER` function or `security_invoker` view (rejected: resolves through caller RLS, so an admin still sees only own rows; `security_invoker = false` gives ungated owner bypass — worse than a gated function; ADR-016).
- A separate admin schema (rejected: PostgREST exposes only `public`; ADR-016).
- One RPC per directory field or a single monolith returning all users (rejected: search+paginate in one bounded RPC is the minimal surface; a single call with all rows is unbounded).
- Pagination by `LIMIT/OFFSET` with eager cap of 25 rows fetched as `26` (adopted) vs keyset pagination on the ordering key (rejected: keyset couples the client to the opaque ordering column and complicates consistent search results across filter changes; the directory is small and offset-capping at 100000 bounds it).
- Wildcard `LIKE '%' || v_search || '%'` search (rejected: `%`/`_` meta-character handling leaks into semantics; `position(substr)` is literal and case-insensitive).

Security impact:
- Non-admin authenticated sessions are denied in-body with `CLOUD-013: admin access required`, including claim-tampered sessions; `anon` and `service_role` hold no EXECUTE; postgres (owner) is also denied without a real admin identity — the gate is authorization, not ACL (verified behaviorally U1–U6).
- The directory returns raw rows, so minimization is enforced by exact contract tests: only the 11 documented keys, no internal UUIDs, no `user_id`/`device_id`/`session_id`, no provider/payment refs, no passwords or raw identity metadata (U16–U19).
- Search and offsets are bounded (100 chars / page 25 / offset ≤ 100000) so client input cannot produce unbounded scans or error text leakage.
- No new data stored beyond the opaque `public_user_id`; it never encodes provider state and is unguessable (UUIDv4 entropy).
- `public_user_id` is immutable even for postgres, so no write path (including maintenance) can silently re-key a user's directory identity.

Performance impact: `public.profiles.public_user_id` UNIQUE adds one index (trivially small). The directory paginates 25+ rows with a bounded offset cap, using the aggregate `LEFT JOIN LATERAL` scans over the existing (tiny) devices/sessions tables; index-assisted by the existing FKs. `COLLATE "C"` ordering avoids locale-aware sort overhead.

Operational impact: One additive migration `20260916120000_establish_admin_user_directory.sql` applied to dev project `zbzhlhoxblguepplqppw` via Supabase MCP, then verified with `db_assertions.sql` and `rls_assertions.sql` plus the security/performance advisors. Reversion is additive-safe: `revoke execute ... from authenticated; drop function public.admin_users(text, integer); drop trigger profiles_guard_public_user_id_immutable on public.profiles; drop trigger profiles_set_public_user_id on public.profiles; drop function ...; alter table public.profiles drop column public_user_id cascade;`.

Testing impact: `db_assertions.sql` grows from 57 to 60 checks — the check 16 whitelist becomes exactly four functions (`admin_metrics_totals`, `admin_metrics_growth`, `admin_metrics_active_users`, `admin_users`); checks 54–56's function-array extends with `public.admin_users(text, integer)` for signature/ACL/SECURITY DEFINER+search-path; new checks 58–60 assert the `public_user_id` column (type, NOT NULL, no default, length CHECK, UNIQUE) and both new triggers (attached to `public.profiles`, not internal, enabled, SECURITY INVOKER, no app-role/PUBLIC EXECUTE, pinned search_path). `rls_assertions.sql` gains the U-block (U1–U21) proving privilege denials for anon/service_role, in-body gate denials for ordinary and claim-tampered sessions and even postgres-without-claims, admin allow with exact projection, search by email/public ID/display_name case-insensitivity, bounded oversized search/offsets, pagination (25/page, has_more, offset 0..100000) reconstructing the deterministic ORDER BY without gaps/dupes, byte-level determinism, data-minimization key-set checks, entitlement/device/session summary exactness, account-status derivation (banned/deleted/active), and `public_user_id` server ownership + immutability on every path. `migration-guard.test.mjs` stays 12/12 (no new table grants; function `grant execute` statements are not matched by the guard's grant-extraction regex). The frontend WEB-009 admin directory wiring (a search box consuming this RPC) remains an explicit future task; the current dashboard honestly reports the directory as not yet wired (apps/website/src/pages/admin.tsx).

Rollback: Additive and reversible per Operational impact above. Prior state: CLOUD-007 metrics baseline, no admin directory function, no `public_user_id` column.

Consequences: The admin dashboard's `AdminTotals/AdminGrowth`-style service gains a typed `admin_users` call surface consuming this RPC (future WEB-009 frontend task); the SECURITY DEFINER whitelist in `db_assertions.sql` check 16 remains the standing guard — any further privileged function must be deliberately added with its own ADR justification. Audio, transcripts, keystrokes, clipboard, and history remain prohibited in Supabase (ADR-010, 01_PRD.md §10).
