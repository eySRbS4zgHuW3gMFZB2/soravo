# ADR-011 — Authentication/session model

Status: Accepted
Date: 2026-09-15

Context: CLOUD-002 introduces the first application table and the authentication foundation for Soravo. The account model (02_TDD.md §12–13) requires an email/password identity that is usable from the web (and later the Tauri desktop shell) and an account/profile representation in Postgres. The public `public` schema is default-deny (ADR-010), so any new table and its access must be introduced with explicit grants, RLS enabled in the same migration, and least-privilege policies. Auth systems are offered by Supabase as a managed service, which brings OWASP-relevant concerns: session transport, secret hygiene (never `service_role` in client code), enumeration resistance, and token origin.

Decision: Use Supabase Auth (email/password) as the identity provider, with Supabase-hosted Postgres for the companion `profiles` table, and supabase-js 2.116.0 (exact-pinned) with the **PKCE flow** (`flowType: "pkce"`) and an intentionally narrow `redirectTo` set: sign-up confirms to `/login`, password reset submits to `/reset-password`. Finished flows route the authenticated user to `/account`.

- Sessions: `persistSession: true` stores the PKCE session in `localStorage` (`sb-<project>-auth-token`), `autoRefreshToken: true` keeps it alive, `detectSessionInUrl: true` consumes the implicit callback parameters for the reset flow. The GC session routes are `/login` (sign-in/sign-up/forgot-password in one page, mode-switched) and `/account` (signed-in dashboard). `/account` renders a sign-in prompt when unauthenticated.
- Profiles: a single-row-per-user `public.profiles` (id = `auth.users(id)` `on delete cascade`, `display_name` ≤80 chars, server-owned `created_at`/`updated_at` via a `SECURITY INVOKER` `BEFORE INSERT OR UPDATE` trigger). Row creation happens lazily from the client on first sign-in (`ensureProfile`); the insert policy's `WITH CHECK` prevents claiming another user's id. No DELETE policy or grant exists in CLOUD-002.
- Least privilege: only `authenticated` receives `select, insert, update` on `profiles`. `anon` and `service_role` get no table privileges and no bypass of RLS. No `SECURITY DEFINER` functions are introduced in `public`.
- Enumeration resistance: every auth failure path returns a generic message (`GENERIC_SIGN_IN_MESSAGE`, `GENERIC_SIGN_UP_MESSAGE`, and the neutral "If that email is registered, a password reset link is on its way.") so upstream messages (e.g. `Invalid login credentials`, `User already registered`) are never shown to clients.
- Client structure: `src/lib/supabase.ts` owns env-gated client creation (no client and no UI when `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are absent), `src/lib/auth-service.ts` owns the service boundaries, and `src/lib/auth-context.tsx` exposes `useAuth()` to pages (with an injectable `client` prop for tests).

Alternatives: GitHub/Google OAuth only (rejected: not self-sovereign, pushes real-linking to later work); a self-built auth server (rejected: unbounded scope, contradicts ADR-010's managed-Postgres posture); storing sessions only in memory (rejected: PKCE + persisted session is the Supabase-recommended, refreshable model for a progressive web app).

Security impact: PKCE replaces the deprecated implicit-grant access token in the URL; localStorage persistence was chosen over cookies to keep the vector narrow and is documented for the Tauri shell to manage. Authenticated requests are driven by the Supabase access token; RLS remains the enforcement boundary via `auth.uid()`, which is server-derived from the token, never from `user_metadata` (ADR-010). The migration pairs its grants with `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` and is structurally enforced by `supabase/tests/migration-guard.test.mjs`. The timestamps trigger function had its `search_path` pinned to `pg_catalog` (Supabase security advisor 0011), applied as a delta migration because the originating migration was already recorded. Entry points validate input shape at the service layer; no client code ever holds a secret.

Performance impact: RLS predicates on `profiles` resolve `auth.uid()` per query; the table is one row per user and is not expected to require additional indexes until CLOUD-003+ introduces worker or entitlement tables.

Operational impact: Auth configuration (email provider, redirect URLs, confirmations) lives in the Supabase project console; schema still lives only in `supabase/migrations/` and is applied through authorized tooling. The `accounts` view of the website becomes operational in the dev project with this foundation.

Testing impact: `supabase/tests/db_assertions.sql` grew to 16 checks (table, RLS on, policy set, no DELETE grant/policy, FK cascade, function invoker rights, anon/service_role SQL-level denial); `supabase/tests/rls_assertions.sql` behaviorally verifies cross-user isolation and anon defaults by impersonating roles and setting `request.jwt.claims`. The website adds the auth service/context/page suites (69 tests across 11 files) using a shared chainable mock client in `src/test-utils/supabase-mock.ts`. Migration-guard structural tests remain 7/7.

Rollback: The delta search-path migration is a `create or replace` and is non-destructive. Reverting the foundation requires DROPping `profiles` (cascades its policies, trigger, and function) and re-running assertions; no payload data would be lost.

Consequences: Auth foundation and profiles are now live in the dev project, wired into the website's `/login` and `/account` pages. Entitlements, device/session records, and admin roles remain explicitly out of scope (CLOUD-004, CLOUD-005, CLOUD-006); the desktop shell will consume the same service layer when account/entitlement UI lands (DESKTOP-006). Storing audio, transcripts, keystrokes, clipboard, or history in Supabase remains prohibited (ADR-010, 01_PRD.md §10).
