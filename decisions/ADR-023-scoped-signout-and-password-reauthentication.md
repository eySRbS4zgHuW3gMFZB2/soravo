# ADR-023 — Scoped sign-out and password reauthentication flows

Status: Accepted
Date: 2026-09-15

Context: CLOUD-008 ("session/password flows") completes the website's active-session and password-management primitives promised by 01_PRD.md §4.9/§6 (password change/reset, logout current session, logout other sessions, session revocation). Two gaps existed in the CLOUD-002 foundation (ADR-011): (1) the account page's "Sign out" called `client.auth.signOut()` with no scope, which defaults to `global` and silently terminates the session on **every** device — wrong semantics for a single current-session logout; (2) when the Supabase project's "secure password change" (reauthentication) rule is enabled, a password update from a session older than the freshness window fails with `reauthentication_needed`, and the website had no flow to satisfy that challenge. Supabase Auth already provides the revocation primitives server-side (GoTrue `/logout?scope=...` deletes the matching `auth.sessions` rows), so no new privileged database surface is required.

Decision:

- **Sign-out is scope-explicit.** `auth-service.signOut(client, { scope })` passes `scope: "local" | "others" | "global"` through to `client.auth.signOut({ scope })` and defaults to `"local"` (match GoTrue's no-arg default of `global` must NOT be inherited). The account page binds "Sign out" to `{ scope: "local" }` (current session only) and adds "Sign out other sessions" bound to `{ scope: "others" }` (terminate all other sessions, keep the current one). No `SIGNED_OUT` event fires for the `others` scope, so the page reports the outcome without unmounting the signed-in view. A global scope remains available for callers that must log out every device.
- **Password change is reauthentication-aware.** `updatePassword` detects the `reauthentication_needed` error code and returns `{ error: null, reauthRequired: true }` instead of a generic failure. The account page then calls `requestReauthentication` (sends an OTP to the user's email/phone via GoTrue) and presents a verification-code field; the code is submitted as the `nonce` to `updateUser({ password, nonce })`. Non-sensitive error codes (`same_password`, `reauthentication_not_valid`, `weak_password`, rate-limit codes) all collapse to the single generic "We couldn't update your password…" message — none leak account state.
- **One service path for the nonce.** The optional `nonce` on `updatePassword` is the single code path for a reauthentication-challenged password change (no separate "verify nonce" helper); the reset link page maps any unexpected reauth challenge to "request a fresh reset link" rather than attempting the challenge inside the recovery flow.
- **No new migration and no new SECURITY DEFINER.** The `public.sessions`/`public.devices` ledger and its one-way `revoked_at` latch (CLOUD-005/ADR-013) remain the app-layer session registry; actual credential revocation happens in Supabase Auth (`auth.sessions`) via scoped `signOut`. The `db_assertions.sql` check-16 SECURITY DEFINER whitelist stays at exactly the three ADR-016 metrics functions. CLOUD-008 changes website TypeScript and tests only.
- **Enumeration resistance is preserved.** Every new failure path returns the same generic, action-shaped wording already used by CLOUD-002 (sign-in/sign-up/reset never reveal whether an email is registered, whether a code was valid, or whether a session exists).

Alternatives:

- A fourth SECURITY DEFINER RPC to revoke `public.sessions` rows (rejected: revocation of the authoritative credential lives in Supabase Auth, not the app ledger; a new RPC would widen the check-16 privileged surface without adding a real revocation capability — scoped `signOut` already deletes `auth.sessions` server-side).
- Adding the `reauthenticate()` nonce handling as a separate top-level service function (rejected: one `updatePassword(input, nonce?)` path keeps the API smaller and prevents callers from a "nonce-less" fallback that would silently produce a strong-password failure).
- Making global the default scope for the account-page sign-out to match the GoTrue default (rejected: "sign out" on the account page must mean the current session per 01_PRD.md §4.9; a separate labeled control handles "other sessions").

Security impact: Local/others scopes terminate the matching server-side sessions; a `scope: "others"` revocation leaves the current device signed in and no `SIGNED_OUT` event fires (documented GoTrue behavior) — the UI reflects that. Reauthentication splits password change into "send OTP" then "apply with nonce", so an attacker who has only a stale session token cannot change the password without fresh proof of identity; GoTrue rate-limits the OTP send. All error coalescing stays generic (V3.x session-management / V2.x credential-transport posture from the security baseline): no email-or-session existence disclosures introduced. Token transport is unchanged (PKCE, ADR-011).

Performance impact: Negligible (one extra GoTrue call in the reauthentication path; no new queries).

Operational impact: The reauthentication OTP feature depends on the Supabase project's password-security settings (email/phone templates) being configured to send the code; the website flow is safe with the feature either way because `reauthentication_needed` is handled explicitly when present.

Testing impact: `auth-service.test.ts` gains scope-forwarding, default-local, reauthRequired detection, same_password/nonce coalescing, and `reauthenticate` failure tests; `account.test.tsx` covers the local/other-scope sign-out buttons and the full code-entry password change; `auth-context.test.tsx` verifies the widened `updatePassword` result and scope forwarding; `reset-password.test.tsx` covers the stale-link reauth case. Repo gates (`pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm audit --prod`, `pnpm test:supabase` 12/12) all pass; migration-guard and DB/RLS assertion suites are untouched because CLOUD-008 introduces no SQL.

Rollback: Pure website revert. No schema, grants, policies, or functions change; reverting this commit removes the scoped sign-out and reauthentication UI while Supabase Auth semantics are unchanged.

Consequences: The website now terminates the correct session scope on "Sign out" and supports terminating other sessions from the account page; password changes satisfy the project's reauthentication rule. The desktop shell will consume the same `auth-service` surface when account UI lands (DESKTOP-006), and the WEB-008 dashboard session list remains a read/display task over the CLOUD-005 `public.sessions` ledger. Storing audio, transcripts, keystrokes, clipboard contents, or history in Supabase remains prohibited (ADR-010, 01_PRD.md §10).
