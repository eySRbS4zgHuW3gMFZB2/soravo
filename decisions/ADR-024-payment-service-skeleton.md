# ADR-024 — Payment service skeleton

Status: Accepted
Date: 2026-09-15

Context: CLOUD-009 ("payment service skeleton") starts the server-side payment capability promised by 01_PRD.md §18 (payment created through a server-controlled flow; server is the price authority; client never submits an amount). No payment function exists yet in the repository: `services/license-api` is only a README placeholder and no payment tables, functions, or secrets exist anywhere. CLOUD-009 must deliver the skeleton only — no live Razorpay integration, no webhook handling, no signature verification, no idempotency ledger, and above all no path that lets a client assert its own price, its own payment status, or its own entitlement (ADR-012 keeps entitlement writes exclusively on the `service_role` path in later phases). The product catalog in 01_PRD.md §8 defines the pricing *targets* (~USD 12/month and ~USD 50 lifetime) that the design must hard-code server-side as `evaluated_target` values, not as live offers and not as client-suppliable data.

Decision:

- **The skeleton lives in the `@soravo/license-api` workspace package under `services/license-api`.** It is TypeScript (type: module, Node) with zero runtime dependencies: no HTTP client, no database client, no Razorpay SDK, and no environment-variable reads. Public entry `src/index.ts` exports `PaymentService`, `ProductCatalog`/`PRODUCT_CATALOG`/`DEFAULT_PRODUCT_CATALOG`, `createPaymentProvider`, `PaymentError`/`PAYMENT_ERROR_CODES`, and the public types. It does NOT export the dev provider machinery.
- **The server is the price authority.** `PaymentService.createOrder(caller, input)` validates the caller's server-derived `userId` (RFC 4122 form) and the client-supplied `productId` against the allow-listed `ProductCatalog` (constructed-time validation: safe-positive integer minor amounts, `USD` only, `evaluated_target`/`confirmed` status, plan must match product id, id must be a known key). Price, plan, and currency come exclusively from the catalog; the accessor ignores extra client fields (`amount`, `price`, `currency`, `plan`, `status`, `verified`, `paidAt`, foreign `reference`/`orderId`, embedded product objects). The `OrderInitiation` result carries only `orderId`, fresh `reference` (UUID v4 by default), `productId`, `plan`, `amountMinor`, `currency`, and `provider` — never a payment status, never a verification flag, never an entitlement.
- **Provider boundary via dependency inversion.** The `PaymentProvider` interface exposes a single `createOrder(CreateOrderRequest)` seam. `DevPaymentProvider` is a deterministic in-process test fake with two behaviors (`success`, `always_fail`); it is internal, never exported from `src/index.ts`, and the factory refuses it under `NODE_ENV=production`. `createPaymentProvider(config, nodeEnv)` takes only an explicit `kind` (`dev` | `razorpay`) — credentials are not accepted and no Razorpay environment variables are ever read; `kind: "razorpay"` throws a stable `provider_not_implemented` error reserved for CLOUD-010. This is the future home of the real Razorpay Orders API adapter, which will receive the server-resolved `amountMinor`/`currency` — never a client value.
- **Failure isolation.** Any provider failure is mapped to a single safe application-level `PaymentError` (`provider_unavailable`, generic message). Logs record only the provider `kind`, the reference, and the error constructor `name` — never the underlying error message, never credentials. `PaymentError` carries a stable machine-readable `code` (`invalid_request`, `invalid_identity`, `invalid_product`, `invalid_configuration`, `provider_unavailable`, `provider_not_implemented`) with safe `message`/`detail`.
- **No database change, no network, no entitlement writes.** CLOUD-009 commits zero SQL: payment/history tables and webhook/`orders` reconciliation belong to CLOUD-010/011, and the idempotency boundary is CLOUD-011. `PaymentService` makes no outbound calls and cannot activate an entitlement (its entire prototype surface is `createOrder`). The `db_assertions.sql` check-16 SECURITY DEFINER whitelist stays at exactly the three ADR-016 metrics functions; no new grants, policies, or functions are introduced.

Alternatives:

- Shipping the skeleton with a `payment_orders`-style table now (rejected: ADR-012 explicitly defers payment history, and an unreconciled table invites half-built RLS and a non-idempotent write path; the skeleton intentionally has no persistence so CLOUD-010/011 can define the real schema once).
- Building the skeleton on the website package (rejected: 14_ENVIRONMENT_AND_SECRETS.md and the repo-wide rule forbid any secret-bearing payment logic in frontend/desktop bundles; `services/license-api` is the mandated server-side boundary).
- Adding a `card`/`paymentMethod` field or client-asserted `amountMinor` in the accessor input (rejected: the client must never influence price, per 01_PRD.md §18 and §16's "server verifies / client never asserts" rules).
- Have `createPaymentProvider` read `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` now (rejected: credential handling belongs to the CLOUD-010 provider implementation; the skeleton must not create a path that even *loads* secrets it cannot safely steward).

Security impact: The skeleton adds no DB surface (no new functions, grants, or policies) and no network surface (no HTTP/WebSocket client, verified by structural tests). Price tampering, status tampering, entitlement self-activation, cross-user reference use, and provider-argument injection are all rejected by construction and covered by the deterministic test suite (anonymous identities → `invalid_identity`; unknown/malformed products → `invalid_product`; client price/status/plan fields ignored; exotic provider references (`kind: "razorpay"`) refused in every environment; dev fake refused in production). Error text never reflects whether a user, product, or payment exists in a way that aids enumeration. Secret references (`RAZORPAY_*`, `process.env`) are absent from `src/**` (also asserted structurally). The dev provider's `providerOrderId` is sanitized to `[A-Za-z0-9_-]` for downstream id-safe persistence in CLOUD-011.

Performance impact: Negligible — one sync UUID generation and an in-process provider call; no I/O.

Operational impact: The package will later run as a server-side service; CLOUD-009 ships no deployment target, no HTTP listener, and no runtime config beyond an explicit in-code provider kind + `NODE_ENV` (`PAYMENT_PROVIDER_KIND=dev|razorpay` documented in `.env.example`, with `RAZORPAY_*` names reserved and commented out, never read). Until CLOUD-010, the only selectable provider is the dev fake.

Testing impact: 41 deterministic Vitest tests across 5 files (`service`, `dev-provider`, `provider-factory`, `catalog`, public `index`): catalog targets documented as `evaluated_target` and validated at construction; anonymous/malformed callers and products rejected before the provider is touched; exact initiation shape (no status/verification/entitlement fields); prototype surface locked to `createOrder`; client-supplied price/status/plan/foreign identifiers ignored; provider failure mapped to the stable safe error with no sensitive log fields; structural "no `process.env`, no `RAZORPAY_*`, no fetch/http client in `src/**`" assertions; dev provider deterministic success/failure; factory gates (`razorpay` → `provider_not_implemented`, dev-in-production → `invalid_configuration`, unknown kind → `invalid_configuration`); public entry omits provider internals. Repo gates (`pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm audit --prod`, `pnpm test:supabase` migration guard) all pass; DB/RLS suites are untouched and `package.json` wires the package into lint/typecheck/test.

Rollback: Pure workspace revert. No schema, grants, policies, or functions change; removing this commit removes the skeleton while the documented catalog targets remain unchanged. No live provider or merchant integration is affected because CLOUD-009 never touches one.

Consequences: The payment capability now has an entrance: a validated, dependency-inverted, server-authoritative `createOrder` surface that CLOUD-010 will extend with a real Razorpay adapter (per official Razorpay Orders API docs, credentials server-side only) and CLOUD-011 with webhooks, signature verification, and the idempotency/reconciliation ledger (per ADR-012's service_role entitlement-write authority). Storing audio, transcripts, keystrokes, clipboard contents, or history in Supabase remains prohibited (ADR-010, 01_PRD.md §10).
